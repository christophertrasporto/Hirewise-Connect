## 0. Mission

Build **Hirewise Connect**, an agency-controlled talent marketplace for Hirewise Virtual Assistance Services.

Clients discover, evaluate, shortlist, and request interviews with Hirewise-verified virtual assistants and outsourced professionals. Hirewise controls pricing, interview coordination, contracts, deposits, deployment, and the official client–agent relationship. Agents enter through the Hirewise VA Academy, get assessed and certified by coaches, and their verified credentials appear on their Connect profile automatically.

The ecosystem in one line:

`Academy → Certification → Connect Profile → Client Shortlist → Sales Coordination → Interview → Selection → Agreement → Deposit → Deployment`

This is **not** a freelancer marketplace. There is no direct client–agent negotiation, no direct messaging between clients and agents before deployment, and no agent-set pricing.

## 1. Non-negotiable invariants

These are enforced in code, tests, and schema. Hiding a UI element is never sufficient.

### 1.1 Commercial
- **INV-C1** `AgentCompensation` and `ClientBillingRate` are separate tables with separate permissions and separate history. No shared "rate" column anywhere. No view, projection, export, or report joins both unless the actor holds `compensation.read` AND `billing_rate.read`.
- **INV-C2** Agents cannot create, edit, propose, or view the change history of `ClientBillingRate`. Agents see only whether a published client rate exists, never the amount. (See Section 14, Q4.)
- **INV-C3** A `ClientBillingRate` is visible to clients only when `status = PUBLISHED`, and publishing requires `billing_rate.approve` (Admin or Super Admin). Sales may propose, never publish.
- **INV-C4** Every rate change (either table) writes a `RateHistory` row with previous value, new value, actor, reason, timestamp, in the same transaction.
- **INV-C5** A `Placement` cannot transition to `ACTIVE` unless its `Deposit.status ∈ {PAID, WAIVED}`. `WAIVED` requires `deposit.override` permission and a non-empty reason, and writes an audit row.
- **INV-C6** No automatic pricing algorithm. No AI matching. Rule-based matching only, and only in Phase 5.

### 1.2 Privacy and contact isolation
- **INV-P1** Agent private contact data (email, phone, exact address, government IDs, resume file) lives in `AgentPrivateContact` and is never included in any client-facing projection.
- **INV-P2** Client private contact data (contact person mobile, direct email) is never included in any agent-facing projection.
- **INV-P3** Clients see only their own `Client`, `ClientRequirement`, `Shortlist`, `InterviewRequest`, `Interview`, `Placement`, `Agreement`, `Invoice`, `Deposit`, `Payment`, and `Notification` rows. Every repository query for these entities is scoped by `clientId` derived from the session, never from request input.
- **INV-P4** `AdminNote` rows are never returned to Agent or Client roles unless `visibility` explicitly equals `AGENT` or `CLIENT`. Default is `INTERNAL`.
- **INV-P5** Coach/Trainer sees only agents enrolled in courses or training groups the coach is assigned to, and never financial data of any kind.
- **INV-P6** Uploaded media (video, audio, resume, portfolio, documents) is served through short-lived signed URLs generated by a service that runs the same authorization check as the API. No public buckets.

### 1.3 Authorization
- **INV-A1** Every service function receives an `Actor` (from the session) and calls `authorize(actor, permission, resource?)` before doing anything. Route handlers and server actions contain no business logic and no Prisma calls.
- **INV-A2** Prisma is imported only inside `src/server/db/` and `src/server/repositories/`. Enforced by an ESLint `no-restricted-imports` rule.
- **INV-A3** All outbound data passes through an explicit allowlist projection in `src/server/views/` (for example `toCandidateClientView`). Spreading a Prisma record into a response is forbidden. Projection tests assert that forbidden keys are absent.
- **INV-A4** State transitions happen only through the entity's state machine module. Direct status updates via repository are forbidden outside that module.

### 1.4 Integrity and audit
- **INV-I1** Certifications originate only from the Academy pipeline (`origin = ACADEMY`) or from a user with `certification.issue` (`origin = ADMIN_ISSUED`). There is no agent-writable path to `Certification`.
- **INV-I2** Agreement acceptance stores the agreement version id, body checksum, user, timestamp, IP, and user agent. A user with any missing acceptance for a currently active required agreement is blocked from all authenticated routes except the acceptance flow.
- **INV-I3** `AuditLog` is append-only. No update or delete path exists in application code. A database trigger rejects `UPDATE` and `DELETE` on the table.
- **INV-I4** Money is stored as integer minor units plus an ISO 4217 currency code plus a `RateUnit` (`HOURLY | MONTHLY`). Never floats.

## 2. Users and roles

| Role key | Name | One-line scope |
|---|---|---|
| `SUPER_ADMIN` | Super Admin / Owner | Everything, including role and permission administration, agreements, deposit policies, and compensation. |
| `ADMIN` | Admin | Talent, clients, certifications, billing rates, placements, interviews, media approval, verification, suspensions. No compensation unless granted. |
| `SALES` | Hirewise Sales Team | Assigned clients, requirements, shortlists, interview coordination, rate proposals, agreements, deposits, placements. |
| `RECRUITER` | Recruiter | Agent pipeline: registrations, profile review, screening notes, availability. No client financials. |
| `COACH` | Coach / Trainer | Assigned courses, enrolled students, assessments, certification recommendations. |
| `OPERATIONS` | Operations Manager | Placements, deployment checklists, active agents, availability, reservations. Read-only on billing rates. |
| `AGENT` | Agent / Talent | Own profile, media, courses, certifications, interviews, placements. |
| `CLIENT` | Client | Own profile, marketplace, own shortlists, interview requests, placements, agreements, invoices, deposits. |

Roles map to permissions through `Role → RolePermission → Permission`. Permissions are string keys (Section 7). A user has exactly one primary role. A Super Admin can grant additional permissions to a user via `UserPermissionOverride` (audited).

### 3.1 Layering (strict)

```

src/server/auth/         session, Actor, MFA

src/server/views/        allowlist projections per role
src/server/repositories/ Prisma queries; the ONLY place Prisma is imported (with db/)
src/server/events/       outbox: domain events → notifications, tasks, audit

src/lib/                 pure utilities, money, dates
prisma/                  schema, migrations, seed
docs/adr/                architecture decision records
docs/                    ERD, walkthroughs, runbooks
```

### 3.2 The `Actor`

```ts
type Actor = {
  userId: string;
  role: RoleKey;
  permissions: Set<PermissionKey>;   // resolved from role + overrides, cached per request
  clientId?: string;                 // present for CLIENT
  agentProfileId?: string;           // present for AGENT
  coachCourseIds?: string[];         // present for COACH
  salesAssignedClientIds?: string[]; // present for SALES
};
```

`authorize(actor, permission, resource?)` throws `ForbiddenError`. Ownership checks live in `policies/ownership.ts` (for example `assertClientOwns(actor, shortlist)`).

### 3.3 Transactions and effects

A state transition = one DB transaction containing: the status update, audit row, rate/deposit side records where relevant, and an `OutboxEvent` row. The worker drains the outbox to create notifications, tasks, and emails. This guarantees the audit trail is never out of sync with the state.

## 5. State machines

Each lives in `src/server/state/<entity>.ts` as a transition table `{ from, to, permission, guard?, effects[] }`. Illegal transitions throw. Every transition audits.

### 5.1 AgentProfile.status
```
DRAFT → SUBMITTED                      (agent; guard: profileCompletion ≥ 80, resume uploaded, ≥1 video SUBMITTED or APPROVED)
SUBMITTED → UNDER_REVIEW               (recruiter/admin)
UNDER_REVIEW → APPROVED                (admin; effect: availability=AVAILABLE unless set, notify agent)
UNDER_REVIEW → REVISION_REQUIRED       (recruiter/admin; requires feedback)
UNDER_REVIEW → REJECTED                (admin; requires reason)
REVISION_REQUIRED → SUBMITTED          (agent)
APPROVED → HIDDEN                      (admin/ops)      HIDDEN → APPROVED
APPROVED → SUSPENDED                   (admin; reason)  SUSPENDED → APPROVED (admin; reason)
```
Client-visible iff `status = APPROVED` and `availabilityStatus ≠ UNAVAILABLE` (PLACED/RESERVED are visible but badged; see Section 14, Q7).

### 5.2 AgentProfile.availabilityStatus
`AVAILABLE | AVAILABLE_SOON | INTERVIEWING | RESERVED | PLACED | UNAVAILABLE | PAUSED`
- Set by Admin/Ops/Recruiter, or automatically: interview scheduled → `INTERVIEWING` (if `AVAILABLE`); reservation created → `RESERVED`; placement `ACTIVE` → `PLACED`; placement `COMPLETED | CANCELLED` → previous status or `AVAILABLE`; reservation expired → previous status.
- Agent may set `PAUSED` for self and set `availableFrom`. Agent cannot set `PLACED` or `RESERVED`.

### 5.3 Video / Recording / Portfolio status
```
DRAFT → UPLOADED → SUBMITTED → UNDER_REVIEW → APPROVED | REJECTED | REVISION_REQUIRED
REVISION_REQUIRED → SUBMITTED
APPROVED → RETIRED (when a replacement is approved)
```
Only `APPROVED` items appear in client projections. Review requires `media.review`. Feedback is required on REJECTED and REVISION_REQUIRED.

### 5.4 InterviewRequest.status
```
REQUESTED → SALES_REVIEW → CLIENT_CONFIRMATION → CANDIDATE_CONFIRMATION → SCHEDULED
SCHEDULED → COMPLETED → CLIENT_DECISION_PENDING → CLOSED
Any pre-COMPLETED → CANCELLED (sales/admin/client-own; reason)
```
Per-candidate decisions live on `Interview.clientDecision`. `SECOND_INTERVIEW` creates a new `Interview` (round+1) under the same request and moves the request back to `CLIENT_CONFIRMATION`. `SELECTED` creates a `Placement` in `SELECTED`.

Effects on `REQUESTED`: notify Sales queue and assigned account manager; create `Task` (type `REVIEW_INTERVIEW_REQUEST`, due +1 business day); write `Introduction` rows; audit `INTERVIEW_REQUESTED`.

### 5.5 Placement.status
```
PENDING → INTERVIEWING → SELECTED → AWAITING_AGREEMENT → AWAITING_DEPOSIT → DEPLOYMENT_PREP → ACTIVE
ACTIVE ↔ PAUSED
ACTIVE | PAUSED → COMPLETED
Any non-terminal → CANCELLED (reason)
```
Guards:
- `SELECTED → AWAITING_AGREEMENT` requires `placement.approve` (this is "Hirewise Approval") and a `PUBLISHED` `ClientBillingRate` snapshot.
- `AWAITING_AGREEMENT → AWAITING_DEPOSIT` requires a `PLACEMENT_SERVICE_AGREEMENT` acceptance or an uploaded signed `Document(kind=SIGNED_AGREEMENT)`.
- `AWAITING_DEPOSIT → DEPLOYMENT_PREP` requires `Deposit.status ∈ {PAID, WAIVED}`.
- `DEPLOYMENT_PREP → ACTIVE` requires all required checklist items done and `startDate` set. Re-checks the deposit guard (INV-C5).

### 5.6 Verification level (ordered)
`PROFILE_SUBMITTED < PROFILE_VERIFIED < SKILLS_ASSESSED < HIREWISE_CERTIFIED < INTERVIEW_READY < DEPLOYMENT_READY`
- Computed by `verification.recompute(agentProfileId)` against `VerificationRequirement` rows after any relevant event.
- Admin may set manually with reason; manual sets are audited and flagged `isManual` until the next recompute confirms them.

### 5.7 Certification.status
`PENDING_REVIEW → APPROVED → EXPIRED | REVOKED`. `ACADEMY` origin enters `PENDING_REVIEW` if the template's requirement says `coachReviewRequired`, otherwise `APPROVED` directly. Expiry job runs daily; "expiring in 30 days" notification.

### 5.8 Reservation.status
`ACTIVE → EXTENDED (n times) → RELEASED | EXPIRED | CONVERTED`. TTL from `Setting.reservationTtlDays` (default 7). Only one `ACTIVE` reservation per agent (partial unique index). Expiry job hourly.

## 8. Workflows

### 8.1 Client registration and onboarding
1. Form: company name, contact person, position, business email, phone, industry, website, country, timezone, services needed, agents required, preferred schedule, expected start date, notes.
2. Business email domain check: reject free-mail domains by default (`Setting.allowFreeMailClients` can relax this). Verify email via magic link.
3. Agreement step: present all active `CLIENT_*` agreements. Each must be opened and individually accepted. Store `AgreementAcceptance` per agreement with IP, UA, checksum. Not a single checkbox.
4. Client status `PENDING_REVIEW` → Sales/Admin reviews → `ACTIVE`. **ASSUMPTION A2:** clients cannot browse talent until `ACTIVE`. Registration notifies the Sales queue (`NEW_CLIENT_REGISTRATION`) and auto-creates `Task(type=QUALIFY_CLIENT)`.
5. Account manager assigned manually by Admin/Sales lead. **ASSUMPTION A3:** no round-robin in MVP; `Setting.autoAssignAccountManager` reserved.

### 8.2 Agent registration and profile pipeline
1. Form: full name, professional name, email, phone, location, timezone, primary role, skills, years of experience, industry experience, resume, availability, preferred schedule, work setup, equipment, internet, software, portfolio. Split into steps; each step saves.
2. Agreement step with all `AGENT_*` agreements, same mechanics as clients.
3. Profile completion % computed from a weighted checklist (personal 15, professional 20, resume 10, skills 10, experience 10, video 20, voice 15). Shown on the agent dashboard with next-step prompts.
4. Submit → Section 5.1 pipeline. Approval triggers `verification.recompute` and a notification.

### 8.3 Talent search (client)
- Filters: role, skill (multi), industry, experience level, certification template, academy course, assessment label (min), availability status, timezone (± hours from client), work setup, languages, software, campaign experience, verification level (min), published rate range.
- Results are `toCandidateCardView` only. Default sort: verification level desc, then availability, then recency of approval.
- Every profile open writes `CandidateView` and upserts `Introduction`.
- The search endpoint applies the visibility predicate server-side; there is no "include hidden" flag reachable by clients.

### 8.4 Shortlist
Add / remove / note / compare (up to 4 side by side: skills, experience, certifications, assessment labels, availability, published rate, verification). Sales sees shortlist activity for assigned clients (poll or SSE). Audit `CANDIDATE_SHORTLISTED`.

### 8.5 Interview request
Client picks shortlisted candidates → fills preferred date/time/timezone, notes, requirement link or inline role/schedule/start date → submit. Effects per Section 5.4. Sales works the request from the Sales dashboard: confirms with client (mediated message + proposed slots), confirms with candidate (agent sees anonymised requirement and slots), schedules (`Interview` row with meeting link entered by Sales). **ASSUMPTION A4:** no calendar or Zoom API integration before Phase 5. After the interview, client records a decision; Sales records internal feedback.

### 8.6 Selection → placement → deposit → deployment
Per Section 5.5. On `SELECTED`: Sales confirms the published billing rate (or proposes a placement-specific rate for Admin approval), generates the service agreement (template with placeholders) or uploads a signed PDF, creates `Deposit` from the default `DepositPolicy` (`ONE_MONTH` = `rate × Setting.hoursPerMonthDefault` when unit is `HOURLY`, or `rate` when `MONTHLY`), issues `Invoice`. Payment recorded manually. **ASSUMPTION A5:** no payment gateway in Phase 4; a `PaymentProvider` adapter interface exists with a `ManualProvider`; Stripe adapter is Phase 5. Deployment checklist template seeded (equipment check, accounts provisioned, schedule confirmed, client kickoff scheduled). Activation → availability `PLACED`, notifications to client, agent, account manager, operations.

### 8.7 Academy → certification → profile
`CourseCompletion` (internal UI or `POST /api/integrations/academy/completions` with HMAC-signed payload) → if template `requiresCoachReview`, create `Task` for the course coach → coach submits `Assessment` with `certificationRecommended` → `Certification` created per `CertificationRequirement` evaluation → `APPROVED` → appears on profile → `verification.recompute` → notification `CERTIFICATION_COMPLETED`. Admin can `certification.issue` directly (audited, `ADMIN_ISSUED`).

### 8.8 Non-circumvention safeguards (practical, not surveillance)
- Contact hiding per Section 6.
- Mediated `InterviewMessage` thread with a soft content filter: outbound messages from Client or Agent containing email addresses, phone numbers, or messaging-app URLs are held for Sales review and raise `ActivityFlag(rule=CONTACT_INFO_IN_MESSAGE)`. Rate keywords ("salary", "per hour", "how much do you make") raise `RATE_DISCUSSION_IN_MESSAGE`. The message is not silently dropped; the sender is told it is pending review.
- `Introduction` ledger per client–agent pair.
- Flags for: client views > N profiles/hour (scraping), repeated shortlist add/remove churn, agent profile edits that add contact details into free text (regex on summary/experience fields).
- Admin: create `Incident`, attach evidence documents, suspend user (with reason), view incident history per user.
- Nothing reads external systems, devices, or private channels.

## 12. Engineering standards

- **Tests that must exist for every service function:** one happy path, one `ForbiddenError` for each role that must not call it, one ownership violation (client A on client B's resource) where applicable.
- **Projection tests:** for each view in `src/server/views/`, a test asserts that a fixture containing every sensitive field produces output with none of the forbidden keys (`personalEmail`, `phone`, compensation `amount`, `salesNotes`, `internalFeedback`, `positioningNotes`, `reviewFeedback` for clients, etc.). Maintain the forbidden-key list in `src/server/views/forbidden-keys.ts`.
- **State machine tests:** every transition in the table has a test; every non-listed pair throws.
- **Isolation e2e (Playwright):** two clients, two agents; assert cross-visibility is impossible via UI and direct URL.
- **Migrations:** Prisma Migrate only; CI fails on drift. The audit-log trigger and partial unique indexes are raw SQL migrations.
- **Seed:** `pnpm db:seed` creates all roles, permissions, agreements (placeholder text), deposit policies, result labels, verification requirements, skills/software taxonomy, 3 coaches, 5 courses, 25 agents at varied stages, 6 clients, shortlists, 4 interview requests, 2 placements at different stages. Deterministic (fixed faker seed). Demo logins printed at the end.
- **Docs per phase:** `docs/walkthrough-phase-N.md` (what was built, how to demo it, seeded accounts), ADRs for every non-trivial decision, ERD in `docs/erd.md` (Mermaid) kept current.
- **Security baseline:** rate limiting on auth and upload endpoints, CSRF on server actions, secure cookies, argon2id, password policy, MFA for Admin/Super Admin, upload MIME sniffing and size caps (video 200 MB, audio 25 MB, docs 10 MB), signed URL TTL 10 minutes, dependency audit in CI, env validated by Zod at boot, no secrets in repo, `.env.example` maintained.
- **Legal text:** never invent it. Seed agreement bodies with clearly marked `LEGAL_PLACEHOLDER` headings describing what each section must cover.
- **Commits:** Conventional Commits, one feature per commit, PR per phase. Do not commit unless asked.
- **Definition of done for a phase:** all acceptance criteria below checked, `pnpm lint typecheck test e2e` green, seed runs clean on a fresh DB, walkthrough written, ERD updated.

## Appendix B — Glossary

- **Agent / Talent** — a virtual assistant or outsourced professional represented by Hirewise.
- **Client Billing Rate** — the price Hirewise presents to clients for an agent. Admin-controlled.
- **Agent Compensation** — what Hirewise pays the agent. Confidential.
- **Placement** — the engagement of one agent with one client for one position.
- **Deposit** — advance payment required before deployment, per a configurable policy.
- **Reservation** — temporary hold on an agent for one client so two sales reps do not promise the same person.
- **Introduction** — the first recorded exposure of an agent to a client; evidence for non-circumvention.
- **Verification level** — Hirewise's ordered trust ladder for an agent, computed from configurable requirements.
